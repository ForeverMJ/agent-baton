# 引き継ぎ

[English](../handoff.md) · [中文](../zh-CN/handoff.md) · 日本語

作業の途中で Codex が利用上限に達したら、同じプロジェクトで Claude Code（または opencode）を開いて *「続けて」* と
言うだけです。baton は、前のエージェントがどこで止まったのかを新しいエージェントが正確に把握できるようにします。
あなた自身についての情報をすべてのフォルダーにまたがって扱う [共有メモリ](shared-memory.md) とは異なり、
引き継ぎはひとつのプロジェクトの進行中の作業を対象とします。

## プロジェクトを準備する

```bash
cd your-project
baton init
```

これにより `.baton/` が作成され、`AGENTS.md` と `CLAUDE.md` に短いブロックが追加されます。このブロックは、
開始時に `.baton/STATE.md`（および、より新しければ `.baton/RESUME.md`）を読み、`STATE.md` を常に最新に保つよう
すべてのエージェントに指示するものです。`.baton/STATE.md`、`AGENTS.md`、`CLAUDE.md` はコミットしてください。

| ファイル | 書き込む主体 | 内容 | git 管理 |
|---|---|---|---|
| `.baton/STATE.md` | エージェント | 長期的なプロジェクトの状態：目標、完了したこと、次のステップ、決定事項、注意点 | する |
| `.baton/RESUME.md` | baton | 直前のエージェントが止まった正確な位置 | しない |
| `.baton/checkpoints/` | baton | 過去の引き継ぎ（セッションごとに 1 ファイル） | しない |
| `AGENTS.md`、`CLAUDE.md` | `baton init` | 上記のルール（マーク付きブロック内） | する |

## 自動（フックを使う場合）

`baton install` を実行していれば、ほかに必要なことはありません。

- **ターンの終了時**、コンテキストの圧縮時、セッションの終了時に、そのエージェント自身のセッションが
  `.baton/RESUME.md` にチェックポイントとして書き出されます。
- **セッションの開始時**、このプロジェクトで別のエージェントがより最近作業していた場合は、そのセッションが
  チェックポイントとして書き出され、短い引き継ぎメモが新しいセッションのコンテキストに入れられます。

つまり流れはこうです。Codex が利用上限に達し、あなたがそのプロジェクトで Claude Code を開くと、Claude Code は
Codex がどこで止まったのかをすでに知っています。フックが動作するのは `baton init` を実行したプロジェクトだけで、
エージェントの動作を妨げたり失敗させたりすることはありません。診断情報は `.baton/hook.log` に出力されます。

## 手動で行う

```bash
baton                          # このプロジェクトの最新セッションをチェックポイントとして書き出す
baton list                     # このプロジェクトに関する全エージェントのセッション
baton capture --from codex     # エージェントを指定
baton capture --exclude claude # 切り替え先のエージェントを除外
baton capture --session 019a   # 特定のセッション（ID の先頭部分）
baton capture --stdout         # .baton/ に書き込まず表示する
baton resume                   # .baton/RESUME.md を表示（フックのないエージェントに貼り付ける用）
```

## チェックポイントの内容

すべてトランスクリプトからコピーされるので、次のエージェントはその内容を信頼できます。

- 当初の目標と、直近のユーザーの依頼
- 最後の ToDo リストまたは計画
- アシスタントの最後のメッセージ
- ✓ / ✗ の印が付いた直近のツール呼び出しと、直近の失敗およびその出力
- 変更されたファイル
- セッションが終了した理由：利用上限、中断されたターン、コマンド実行中の停止など
- 判明している場合は、エージェントの利用枠の使用状況（Codex）
- `git status` と `git diff --stat`

モデルは呼び出しません。費用はかからず、オフラインで動作し、あなたのコードをどこにも送りません。
チェックポイントの解釈は次のエージェントに任されます。

<a id="several-clones-of-one-repository"></a>
## 同じリポジトリの複数のクローン

セッションはフォルダーで照合されます。リポジトリのクローンを 2 つ持っている場合（たとえば Windows 側と WSL 側に 1 つずつ、
あるいは git worktree）は、リポジトリ単位の照合を有効にしてください。

```json
// .baton/config.json (コミットする)
{ "match": "repo" }
```

コマンドごとに指定することもできます：`baton list --match repo`。クローンはリモート URL
（`https://github.com/o/r.git` = `git@github.com:o/r`）で、リモートがない場合はルートコミットで識別されます。
対象となるのは過去 30 日以内のセッションだけです。別のクローンからのチェックポイントには、そのパスとブランチとともに
**⚠ Different clone** という警告が付きます。そのクローンのコミットされていない変更は、あなたの作業ツリーには
含まれていないためです。

別の環境（WSL ↔ Windows）のエージェントについては、[Windows + WSL](windows-wsl.md) を参照してください。
